# Guía de estudio — 02. La base de datos

## 1. Dos motores, el mismo código

| Motor | Cuándo se usa | Dónde |
|---|---|---|
| **PostgreSQL 17 en Supabase** (nube) | Si existe `config/bd.properties` con `bd.motor=postgresql` | Proyecto `sistema-ventas` en Supabase. La comparten el escritorio y el celular |
| **SQLite** (local) | Si no existe ese archivo | `datos/sistema_ventas.db`, un solo archivo que se crea solo |

`ConexionBD` decide al arrancar:

```java
Properties config = leerConfiguracion();
if (config != null && "postgresql".equalsIgnoreCase(config.getProperty("bd.motor", "").trim())) {
    motor = Motor.POSTGRESQL;
    conectarPostgres(config);          // JDBC a Supabase
    crearEsquemaPostgres();            // ejecuta bd/esquema-postgresql.sql
    CopiadorBD.importarSqliteSiVacia(conexion, new File(ARCHIVO_BD));
} else {
    conectar();                        // jdbc:sqlite:datos/sistema_ventas.db
    crearTablas(conexion);             // CREATE TABLE IF NOT EXISTS ...
    MigradorDatos.instancia().migrarSiVacio(conexion);
}
```

Los DAO usan **SQL estándar**, así que funcionan con los dos motores. Lo específico de cada uno está solo en `ConexionBD`.

| Diferencia | SQLite | PostgreSQL |
|---|---|---|
| Montos | `REAL` | `NUMERIC(12,2)` (exacto) |
| `id` automático | `INTEGER PRIMARY KEY AUTOINCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` |
| Llaves foráneas | Hay que activarlas en cada conexión: `PRAGMA foreign_keys = ON` | Siempre activas |
| Creación del esquema | `ConexionBD.crearTablas` | Script `bd/esquema-postgresql.sql` |

El script de PostgreSQL es **idempotente**: usa `CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION` e inserciones con `WHERE NOT EXISTS`, así que se ejecuta en cada arranque sin duplicar nada. Así se actualiza la base de la nube cuando hay tablas o funciones nuevas.

## 2. Las tablas

Hay **13 tablas del sistema** y, solo en la nube, **`sesiones_app`** para las sesiones del celular.

| Tabla | Columnas principales | Para qué |
|---|---|---|
| `categorias` | id, nombre (único), descripcion | Clasificar productos |
| `productos` | id, codigo (único), nombre, precio, existencia, categoria_id | Catálogo e inventario |
| `clientes` | id, nit (único), nombre, direccion, telefono (principal) | Clientes |
| `telefonos` | id, cliente_id, numero, tipo (`CHECK`: PERSONAL, TRABAJO, CASA, OTRO) | Varios teléfonos por cliente |
| `empleados` | id, codigo_empleado (único), nombre, nit, telefono, puesto | Empleados |
| `proveedores` | id, nit (único), nombre, direccion, telefono, correo | Proveedores |
| `usuarios` | id, usuario (único), nombre, clave_hash, salt, rol (`CHECK`: ADMINISTRADOR, VENDEDOR), activo | Inicio de sesión |
| `facturas` | id, numero_factura (único), nit, cliente, fecha, total | Encabezado de venta |
| `factura_detalles` | id, factura_id, producto, cantidad, precio, subtotal, producto_id | Líneas de la venta |
| `compras` | id, numero_compra (único), proveedor_id, usuario_id, fecha, total | Encabezado de compra |
| `compra_detalles` | id, compra_id, producto_id, cantidad, costo_unitario, subtotal | Líneas de la compra |
| `ordenes_venta` | id, numero_orden (único), cliente_id, usuario_id, fecha, estado (`CHECK`: PENDIENTE, CONFIRMADA, ANULADA), observaciones, total | Pedidos del celular |
| `orden_venta_detalles` | id, orden_venta_id, producto_id, cantidad, precio_unitario, subtotal | Líneas de la orden |
| `sesiones_app` (nube) | token (UUID), usuario_id, creada, expira | Sesiones del celular (8 horas) |

## 3. Relaciones y reglas de borrado

| Relación | Tipo | Al borrar el padre |
|---|---|---|
| `telefonos.cliente_id → clientes` | 1 a N | **CASCADE**: se borran los teléfonos |
| `productos.categoria_id → categorias` | N a 1 | **SET NULL**: el producto queda sin categoría |
| `compras.proveedor_id → proveedores` | N a 1 | **RESTRICT**: no se borra un proveedor con compras |
| `compras.usuario_id → usuarios` | N a 1 | **SET NULL**: la compra se conserva |
| `compra_detalles.compra_id → compras` | 1 a N | **CASCADE** |
| `compra_detalles.producto_id → productos` | N a 1 | **RESTRICT**: no se borra un producto con compras |
| `factura_detalles.factura_id → facturas` | 1 a N | **CASCADE** |
| `factura_detalles.producto_id → productos` | N a 1 | **SET NULL**: la factura conserva el nombre del producto |
| `ordenes_venta.cliente_id → clientes` | N a 1 | **RESTRICT** |
| `ordenes_venta.usuario_id → usuarios` | N a 1 | **SET NULL** |
| `orden_venta_detalles.orden_venta_id → ordenes_venta` | 1 a N | **CASCADE** |
| `orden_venta_detalles.producto_id → productos` | N a 1 | **RESTRICT** |
| `sesiones_app.usuario_id → usuarios` | 1 a N | **CASCADE** |

- **CASCADE** = los hijos mueren con el padre (composición: detalles de factura, teléfonos).
- **SET NULL** = el hijo sobrevive sin el padre (agregación: producto sin categoría).
- **RESTRICT** = no se deja borrar el padre mientras tenga hijos (integridad).

**Diseño de "foto" en facturas:** `facturas` guarda el NIT y el nombre del cliente como texto, y `factura_detalles` el nombre del producto. Así la factura conserva los datos tal como estaban el día de la venta aunque después se cambie o borre el cliente o el producto. `factura_detalles.producto_id` sirve para descontar y devolver existencia. Por eso `facturas` no tiene llave foránea a `clientes`.

**Teléfono principal:** `clientes.telefono` guarda el primer teléfono de la lista porque lo usan los reportes y la tabla de clientes; la lista completa está en `telefonos`.

## 4. Transacciones

Se guardan todas las operaciones o ninguna (`setAutoCommit(false)` + `commit` / `rollback`):

| Operación | Qué incluye |
|---|---|
| Guardar factura | Encabezado + detalles + descuento de existencia. Si un producto no alcanza → rollback |
| Eliminar factura | Devolver existencia + borrar (detalles en cascada) |
| Guardar compra | Encabezado + detalles + suma de existencia |
| Anular compra | Restar existencia (se rechaza si ya no alcanza) + borrar |
| Teléfonos de un cliente | Borrar los anteriores + insertar los de la lista |
| Orden de venta (nube) | La función `app_registrar_orden_venta` corre completa o PostgreSQL revierte todo |
| Factura desde el celular (nube) | `app_registrar_factura`, igual, con descuento de existencia |

Fragmento real de `FacturaDAOSQLite.guardar`:

```java
conexion.setAutoCommit(false);
// INSERT INTO facturas ... (RETURN_GENERATED_KEYS para obtener el id)
guardarDetalles(conexion, factura);           // INSERT INTO factura_detalles ... (en lote)
if (!descontarExistencia(conexion, factura)) { // UPDATE ... WHERE existencia >= ?
    conexion.rollback();
    return false;
}
conexion.commit();
```

**¿Por qué `WHERE existencia >= ?`?** Si dos vendedores venden el último producto al mismo tiempo, el segundo `UPDATE` no encuentra fila que cumpla (afecta 0 filas), y la factura se revierte. Así la existencia nunca queda negativa.

**Números correlativos:** `FAC-`, `COM-` y `OV-` se calculan con el mayor número de la tabla + 1. En la nube, las funciones bloquean la tabla (`LOCK TABLE … IN SHARE ROW EXCLUSIVE MODE`) para que dos peticiones simultáneas no reciban el mismo número.

## 5. Migraciones y datos

- **Bases antiguas:** al abrir el sistema se crean las tablas nuevas y las columnas que falten (`agregarColumnaSiFalta`), sin perder datos.
- **Teléfonos:** al crear `telefonos`, el teléfono que tenía cada cliente se copió como `PERSONAL` (28 clientes migrados).
- **CSV antiguos:** `MigradorDatos` los importa una sola vez si la base local está vacía.
- **Primera conexión a la nube:** si la nube está vacía y hay una base SQLite con datos, `CopiadorBD` la sube conservando los `id`.

## 6. Respaldo y restauración

- **Respaldo:** *Administración → Respaldar base de datos* → archivo `.db` (se abre con DB Browser for SQLite). Local: `VACUUM INTO`. Nube: `CopiadorBD` copia todas las tablas.
- **Restaurar en local:** reemplazar `datos/sistema_ventas.db` y quitar `config/bd.properties`.
- **Restaurar en la nube:** con la nube vacía, poner el respaldo como `datos/sistema_ventas.db` y abrir en modo nube.

## 7. Seguridad de la base en la nube

- **RLS activo en las 14 tablas y sin políticas:** nadie puede leer ni escribir las tablas directamente por la API. Una lectura directa responde **401**.
- **Permisos revocados** a los roles públicos de Supabase (`anon`, `authenticated`).
- La API solo puede **ejecutar** las funciones `app_*`, que validan el token de sesión (ver archivo 03).
- La contraseña de la base solo está en `config/bd.properties` (ignorado por Git). En GitHub solo está `bd.properties.ejemplo`.

## 8. Consultas útiles (para mostrar en clase)

```sql
-- Órdenes de venta que llegaron del celular
SELECT o.numero_orden, o.fecha, c.nombre, o.estado, o.total
FROM ordenes_venta o JOIN clientes c ON c.id = o.cliente_id
ORDER BY o.id DESC;

-- Teléfonos de un cliente
SELECT c.nombre, t.numero, t.tipo
FROM clientes c JOIN telefonos t ON t.cliente_id = c.id
WHERE c.nit = '8888888-8';

-- Productos por agotarse
SELECT codigo, nombre, existencia FROM productos WHERE existencia <= 5 ORDER BY existencia;
```

En NetBeans: *Services → Databases → (conexión) → Execute Command*. En Supabase: *SQL Editor* o *Table Editor*.
